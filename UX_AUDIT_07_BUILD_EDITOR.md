# Пункт 7 — консолідований аудит редактора білду Flake

Дата аудиту: **2026-11-10**.

Спільні ActionResult/error/state contracts пункту 6, згадані в рекомендаціях, є **запропонованими, а не реалізованими**.

**Рекомендований напрям: локальна чернетка + атомарне «Застосувати», інтегровані зі спільними ActionResult/error/state contracts пункту 6.** Не розвивати паралельну систему результатів редактора й не перебудовувати весь інтерфейс у першій ітерації.

## Межі й достовірність

- Робота **read-only**: файли не змінював, скриптів, тестів чи документів не створював.
- Переглянув редактор, picker, preview, каталог/layout, модель і persistence білду, безпосередні мережеві залежності, релевантні metadata/locales/tests.
- Джерело істини — актуальний код. Persistence вже реалізований; архітектурна карта в цьому місці застаріла.
- Версії з build-файлів: Minecraft **26.3**, Java **25**.
- **Тести не запускав; клієнт, screenshots і runtime-поведінку не перевіряв.**
- Нижче **підтверджений дефект** означає проблему, яку можна встановити з прочитаного коду. Невизначений візуальний або платформний ефект позначено окремо.

Пріоритети: **P1** — ризик втрати або хибного розуміння стану; **P2** — суттєва функціональна/UX-неузгодженість; **P3** — локальна незручність.

## 1. Підтверджені дефекти

### 1.1. Синхронізація, pending, помилки й persistence

### E01 — P1. Дві секунди очікування помилково трактуються як відмова

**Доказ:**
- `src/client/java/dev/flake/client/editor/BuildEditorScreen.java:120–135`
- `src/main/resources/assets/flake/lang/uk_ua.json:361`

**Тригер:** команда або актуальний HUD затримуються понад дві секунди.

**Поведінка:** редактор замінює чернетку останнім відомим серверним білдом і повідомляє: «Сервер не підтвердив зміну. Білд відновлено».

**Наслідок:** команда не скасована й може виконатися пізніше. Після наступного HUD білд знову зміниться. UI видає **невідомий результат** за завершену відмову.

---

### E02 — P1. Немає ідентичності окремих змін і коректного узгодження pending

**Доказ:**
- `src/client/java/dev/flake/client/editor/BuildEditorScreen.java:31–35,120–135`
- `src/main/java/dev/flake/editor/EditorCatalog.java:123–128`

**Тригер:** кілька виборів до отримання підтвердження; або зовнішня зміна білду командою під час pending.

**Поведінка:**
- Кожен вибір перезаписує єдиний `draft`, `pending`, `sentAt`.
- Надсилається команда одного слота, але підтвердження визначається за рівністю **всього** білду.
- Новий серверний стан, який відрізняється від optimistic draft, під час pending не переноситься в чернетку.

**Наслідок:** неможливо встановити, яка саме зміна прийнята чи відхилена. Чернетка може тимчасово містити комбінацію, якої сервер не приймав, і маскувати зовнішнє оновлення до таймауту.

Це проблема контракту, **не твердження про перестановку TCP-пакетів**. Самі швидкі послідовні успішні зміни не обов’язково завершуються неправильно.

### E03 — P2. Конкретна серверна відмова не доходить до редактора

**Доказ:**
- `src/main/java/dev/flake/build/LoadoutCommands.java:282–292`
- `src/client/java/dev/flake/client/editor/BuildEditorScreen.java:127–135`

**Тригер:** сервер відхиляє зміну через фактичний lock або невалідний candidate.

**Поведінка:** причина надсилається як command feedback. Редактор її не пов’язує з вибором і чекає свого generic timeout.

**Наслідок:** користувач не отримує своєчасного пояснення біля проблемного слота. Затримка, блокування й помилка валідації виглядають однаково.

### E04 — P1. Завершення pending не означає успішного запису на диск

**Доказ:**
- `src/main/java/dev/flake/build/LoadoutManager.java:38–40,72–78`
- `src/client/java/dev/flake/client/editor/BuildEditorScreen.java:127–135`

**Тригер:** `IOException` при збереженні: права, місце на диску, помилка файлової операції.

**Поведінка:** менеджер уже оновив кеш; помилка запису лише логується. HUD містить новий білд, і редактор завершує pending.

**Наслідок:** білд працює в поточній сесії, але після очищення кешу/reconnect/restart може повернутися старий. UI не розрізняє прийняття сервером і persistence.

Точного напису «Збережено» зараз немає; дефект — відсутність повідомлення про невдале збереження.

### E05 — P1. Помилка завантаження непомітно підміняється default; наступна зміна може перезаписати проблемний файл

**Доказ:**
- `src/main/java/dev/flake/build/LoadoutStore.java:25–44,65`
- `src/main/java/dev/flake/build/LoadoutManager.java:25–35`

**Тригер:** пошкоджений файл, невідома версія, невідоме enum-значення, помилка читання; також збережений невалідний білд.

**Поведінка:** ці ситуації не відрізняються для споживача від відсутності файлу. Менеджер повертає default.

**Наслідок:** редактор не повідомляє, що особистий білд не завантажився. Наступний успішний вибір може замінити проблемний файл без явного рішення про відновлення/reset.

**Відсутній файл у нового гравця — нормальний випадок**, не помилка.

### E06 — P2. Stale HUD залишається джерелом «актуального» редагованого білду

**Доказ:**
- `src/client/java/dev/flake/client/editor/BuildEditorScreen.java:44–48`
- `src/client/java/dev/flake/client/ui/FlakeUiClient.java:48–49`

**Тригер:** HUD перестав оновлюватися, але останній payload досі ненульовий.

**Поведінка:** `hudFresh()` існує, але редактор його не використовує. Рішення про lock спирається на старий стан.

**Наслідок:** користувач не знає, що працює зі stale-даними, і може надсилати зміни за вже неактуальних умов.

### E07 — P2. Перебудова widgets має мережеві побічні ефекти

**Доказ:**
- `src/client/java/dev/flake/client/editor/BuildEditorScreen.java:50–56,137`
- `src/client/java/dev/flake/client/ui/FlakeUiClient.java:61–64`

**Тригер:** `init()` при відкритті/поверненні або `rebuildWidgets()` після зміни білду чи lock.

**Поведінка:** викликається глобальна `action(QUERY, "")`. Якщо глобальний pending дозволяє надсилання, QUERY очищає спільну помилку й встановлює спільний pending.

**Наслідок:** локальна перебудова інтерфейсу впливає на мережевий стан інших екранів і може прибрати їхнє повідомлення про помилку.

Це редакторна точка інтеграції з пунктом 6: **жодних QUERY в init/rebuild**, оновлення — через спільний lifecycle.

### 1.2. Lock, picker, пошук і фільтри

### E08 — P2. Клієнтський lock суперечить серверним правилам ready/countdown

**Доказ:**
- `src/client/java/dev/flake/client/editor/BuildEditorScreen.java:45–48`
- `src/main/java/dev/flake/build/LoadoutCommands.java:282–300`
- `src/main/java/dev/flake/duel/DuelRuntime.java:134–135,191–195`

**Тригер:** гравець ready або перебуває в COUNTDOWN.

**Поведінка:** UI блокує зміну. Сервер ready не вважає таким lock: прийнята зміна скидає готовність. COUNTDOWN також не входить у цей серверний lock; зміна білду скасовує відлік.

**Наслідок:** дія доступна через команди, але недоступна в редакторі. Власного переходу «редагувати та зняти готовність» немає.

Виправлення має використовувати серверну eligibility та спільні дії пункту 6, **не перевизначати lifecycle дуелі**.

### E09 — P2. Відкритий picker продовжує обіцяти вибір після зміни lock

**Доказ:**
- `src/client/java/dev/flake/client/editor/ItemPickerScreen.java:105–107,138,196–217`
- `src/client/java/dev/flake/client/editor/BuildEditorScreen.java:120–121`

**Тригер:** ready/фаза змінюються при відкритому picker без зміни самого білду.

**Поведінка:** picker оновлюється за signature білду, а не доступності редагування. `eligible` враховує лише `candidate.errors()`. Рядок залишається «ОБРАТИ», але `choose()` мовчки повертається через lock.

**Наслідок:** видима дія не працює і не пояснює причини.

### E10 — P2. Фільтр «Меч» пропускає Порожнього Паладина

**Доказ:**
- `src/main/java/dev/flake/editor/EditorCatalog.java:25–29,98–102`
- `src/main/resources/assets/flake/lang/uk_ua.json:100–103,196`

**Тригер:** вибір фільтра типу «Меч».

**Поведінка:** тег меча визначається через `item.name().contains("SWORD")`. `VOID_PALADIN` тег не отримує, хоча його категорія — «Меч · Ближній бій». Повна категорія не дорівнює фільтру «Меч».

**Наслідок:** зброя цього типу зникає з відповідного фільтра. Текстовий пошук і фільтр дають неузгоджені результати.

### E11 — P2. Пошук класів не індексує їхні показані ролі та здібності

**Доказ:**
- `src/main/java/dev/flake/editor/EditorCatalog.java:25–29,116–117`
- `src/client/java/dev/flake/client/editor/ItemPickerScreen.java:141–147,210–214`

**Тригер:** пошук «Захисник» або «Щитовий таран».

**Поведінка:** роль і назви здібностей є у відображенні Бастіона, але відсутні в searchable metadata його `Choice`.

**Наслідок:** користувач не знаходить клас за інформацією, яку сам список використовує для його опису.

### 1.3. Локалізація й навігація

### E12 — P2. Серверний feedback редакторних команд частково жорстко український і технічний

**Доказ:**
- `src/main/java/dev/flake/build/LoadoutCommands.java:285,298,300–301,363–369`

**Поведінка:** повідомлення lock та успішний підсумок формуються `Component.literal` з українськими рядками; підсумок містить enum-назви.

Рішення — **спільні reason codes та args з клієнтською локалізацією**, не окрема таблиця серверних помилок редактора.

## 3. UX gaps, відділені від дефектів

### G1. Порівняння заховане в tooltip

`src/client/java/dev/flake/client/editor/ItemPickerScreen.java:148–162`.

Користувач має утримувати наведення або фокус, щоб прочитати основне порівняння. Рядок одночасно є носієм інформації й миттєвою дією вибору. Немає стабільного місця для уважного рішення.

**Потрібно:** видима detail/comparison область або окремий detail view на компактному GUI. Не обов’язково в мінімальній першій ітерації.

### G2. Недостатньо інформації для вибору класу

Показано загальний опис, роль і назви здібностей, але не їхні умови, cooldown, тривалість і значущі синергії.

Приклад: щит змінює шкоду тарана Бастіона з 4 до 6 HP — `src/main/java/dev/flake/ability/ClassSkills.java:105–116`. Це важлива інформація для складання білду, а не бойовий feedback.

**Потрібно:** дві картки здібностей із фактичними призначеними клавішами й перевіреними параметрами.

### G3. Немає безпечного циклу експериментування

Немає reset змін, undo/redo, відмінності між чернеткою і підтвердженим комплектом. Вихід не пояснює долю pending.

**Перша потреба:** чернетка, Apply, Reset і захист виходу.  
**Наступна:** короткий локальний undo. Redo та presets не є умовою першого релізу.

### G4. Перестановка й перерозподіл бюджету залежать від порядку команд

Для swap потрібен проміжний `NONE`. Для дорожчої заміни іноді спочатку треба здешевити інший слот.

Це наслідок мутацій по одному слоту, а не зламаного бюджету.

**Потрібно:** атомарне застосування фінальної комбінації; окрема кнопка swap може з’явитися пізніше як зручність.

### G5. Бюджет інформує, але мало допомагає

Показано total та ціну варіанта, але не постійно видно:
- залишок;
- внесок кожного слота;
- післявибірний total;
- конкретне «бракує N».

Недоступні варіанти не варто повністю приховувати: вони допомагають зрозуміти, заради чого перебудовувати білд.

### G6. Характеристикам бракує контексту, а не «загального рейтингу сили»

Поточні числа — переважно **стартова база**. Fury, regeneration, lifesteal, cooldown reduction та умовні ефекти не мають адекватного відображення в п’яти числових колонках.

**Потрібно:** явно назвати базовий контекст і показувати механіки окремо. Не виводити вигаданий DPS, бойову ефективність або одну «силу білду».

### G7. Preview не допомагає порівнювати кандидата й фактичну видачу

Манекен показує вже обраний draft, але не candidate до вибору. Немає схеми hotbar/offhand.

Реальна видача ущільнює непорожні hotbar items, а shield йде в offhand — `src/main/java/dev/flake/duel/DuelRuntime.java:309–330`. Через це «активний слот 1/2» не слід подавати як гарантований номер hotbar.

### G8. Фільтри й keyboard navigation потребують стабільності

- Фільтр категорії та ціни перебирається циклічно, без огляду варіантів.
- `refresh()` видаляє й створює dynamic widgets — `ItemPickerScreen.java:65–102`.
- Новий picker не зберігає попередній пошук/позицію.
- Стрілки пагінації мають лише символи, без контекстних назв сторінок.

**Не перевірено runtime:** втрата/стрибки фокусу після refresh. Не називаю це вже доведеним keyboard-багом.

### G9. Довгий текст переважно обрізається

`src/client/java/dev/flake/client/ui/UiTheme.java:53–57,113–115`.

Основні описи — однорядкові ellipsis. Tooltip повертає частину змісту, але не є достатньою основою для всіх довгих описів.

**Потрібно:** scrollable details, а не нескінченне зменшення шрифту.

**Не перевірено:** фактичне обрізання tooltip за краєм екрана, перекриття badges і заголовків, реальна читабельність на всіх масштабах.

### G10. Броня — окреме product decision

Підтверджено:
- броня не входить у cost — `src/main/java/dev/flake/build/Loadout.java:84–87`;
- diamond має найкращі захисні показники — `Loadout.java:241–246`;
- default — iron — `Loadout.java:204–206`;
- бонус повного сету не заявлений як реальний.

Це робить частину вибору слабко мотивованою, але **не дає підстав мовчки змінити ціни, числа чи стартовий комплект**. UI має чесно пояснювати чинні правила; ребаланс — окреме рішення.

## 4. Рекомендована модель: explicit apply transaction

### 4.1. Один основний цикл

**Завантажити авторитетний білд → оглянути → змінити чернетку → застосувати атомарно.**

- Baseline: підтверджений білд і `stateRevision`.
- Draft: локальні зміни selectable fields.
- Вибір у picker змінює лише draft; preview і прогноз характеристик реагують одразу.
- Змінені слоти позначені.
- Постійні дії: **«Застосувати»**, **«Скинути зміни»**, **«Назад»**.
- Reset повертає baseline, а не стартовий комплект.
- Проміжна чернетка може бути надбюджетною або містити дублікат для планування. **Сервер вирішує допустимість фінального застосування.**
- Відхилення не знищує draft.

### 4.2. Спільна інфраструктура пункту 6

Використати спільний:

`ActionResult(requestId, reasonCode, args, stateRevision)`

Для операції Apply потрібні:
- повний candidate;
- `requestId`;
- очікувана revision;
- чинний серверний eligibility/lock contract.

Не створювати:
- окремий generic result dispatcher редактора;
- окремий глобальний error cache;
- власний polling/query lifecycle;
- дублюючі правила ready або preparation checklist.

Редактор лише відображає відповідні серверні причини та за потреби підсвічує конкретний слот.

### 4.3. Узгодження результату й стану

- Один in-flight apply у першій ітерації.
- Повтор того самого запиту не застосовує його двічі.
- `ActionResult` корелює операцію; відповідний авторитетний стан формує новий baseline.
- Якщо результат і snapshot приходять у різному порядку, UI не завершує операцію за випадковим збігом білду.
- За revision conflict немає silent overwrite. Draft залишається; користувач отримує можливість переглянути актуальний baseline і вирішити, як перенести зміни.
- Таймаут означає **«результат ще невідомий»**, не автоматичну відмову.
- Відновлення актуального стану використовує спільний lifecycle пункту 6 — без QUERY з init/rebuild.

### 4.4. Persistence contract

Бажаний мінімальний контракт:
1. перевірити revision, eligibility і candidate;
2. забезпечити збереження;
3. опублікувати прийнятий білд/revision і виконати пов’язані серверні наслідки;
4. повернути спільний результат.

Помилка persistence не повинна видаватися за успішно збережений комплект. Не можна залишати готовність чи кеш у частково зміненому стані.

«Записано файл» також не слід автоматично прирівнювати до гарантії пережити довільне вимкнення живлення: точна durability-гарантія — окремий контракт сховища.

### 4.5. Ready та lock

Не дублювати основний lifecycle:

- Огляд і порівняння дозволені навіть у read-only стані.
- Дія **«Редагувати та зняти готовність»** використовує спільну серверну дію пункту 6.
- Countdown-поведінка пояснюється згідно з обраними серверними правилами.
- Якщо lock виник при відкритому picker або dirty draft, робота зберігається, можливості оновлюються, причина видима.
- Успіх Apply, а не перегляд candidate, запускає серверні наслідки зміни білду.

### 4.6. Вихід і disconnect

- Clean draft: звичайне повернення.
- Dirty draft: **застосувати й вийти / відкинути / залишитися**.
- Pending: не називати вихід скасуванням уже надісланої операції.
- Disconnect: немає повідомлення про успішне застосування без результату.
- Локальну чернетку не переносити непомітно на інший сервер/світ.
- Збереження чернетки між reconnect можна додати пізніше; для першої ітерації достатньо чесної поведінки без неправдивої гарантії відновлення.

### Чому не autosave + undo

| Варіант | Перевага | Ціна |
|---|---|---|
| **Explicit apply** | Атомарні зміни, простий reset, контрольований вихід, експерименти не змінюють серверний білд | Одне додаткове натискання |
| Autosave + undo | Швидкий одиничний вибір | Черга мутацій, undo як нова серверна зміна, часткові відмови; swap/presets усе одно потребують транзакцій |

Для редактора комплекту explicit apply — простіша й передбачуваніша основа. Не рекомендую витрачати першу ітерацію на складний autosave-перехідник.

## 6. Acceptance scenarios

### 6.1. Детерміновані перевірки моделі й контрактів

| Сценарій | Очікуваний результат |
|---|---|
| Вибір будь-якого слота | Змінюється тільки draft; немає мережевої мутації |
| Reset | Повертає останній підтверджений baseline |
| Бюджет 6 → інша валідна комбінація | Один atomic Apply, без проміжних серверних комплектів |
| Невалідний фінальний candidate | Сервер відхиляє весь білд; жоден слот не застосований |
| Swap двох active items | Фінальний валідний стан застосовується атомарно |
| Revision conflict | Серверний білд не перезаписаний; draft збережений |
| Повтор `requestId` | Немає повторної мутації або повторних побічних ефектів |
| Результат до snapshot / snapshot до результату | Однаковий кінцевий стан; немає false success |
| Затримка понад 2 с | Статус невідомого результату, без вигаданої відмови |
| Зовнішня команда під час редагування | Немає тихого overwrite локальних чи серверних змін |
| Помилка persistence | Немає неправдивого успіху та частково оновленого стану |
| Missing save | Коректний новий/default білд |
| Corrupt/unsupported/unreadable save | Відмінний результат завантаження; немає silent overwrite |
| Rebuild/resize/повернення з picker | Не створюють QUERY та не очищають спільну помилку |
| Фільтр «Меч» | Включає Void Paladin |
| Пошук ролі/здібності | Знаходить відповідний клас |
| Локалізація reason codes | Коректні тексти й аргументи uk/ru/en |

### 6.2. Клієнтські інтеграційні сценарії

- Loading → authoritative baseline без можливості застосувати placeholder.
- Stale → відновлення актуальності без втрати draft.
- Lock змінюється при відкритому picker: немає оманливого «ОБРАТИ».
- Ready редагується через погоджену спільну дію; перегляд не змінює ready.
- Dirty exit, clean exit і pending exit мають різну, передбачувану поведінку.
- Disconnect під час apply не породжує false success; результат старого контексту не застосовується до нового.
- Інші екрани не втрачають свої повідомлення через перебудову редактора.

### 6.3. Що потребує runtime-перевірки

**Layout і текст**
- GUI 320×240, 427×240, 480×270 та більші; різні GUI scale.
- Довгі українські/англійські/російські назви.
- Badges, header, footer, scrollable details і tooltips без перекриття.
- У compact layout `EditorLayout.java:11` задає header 30, тоді як divider малюється на `BuildEditorScreen.java:145` через 32 одиниці від верху. Числова неузгодженість є; практичний візуальний ефект **не перевірено**.

**Клавіатура й доступність**
- Повний сценарій без миші.
- Фокус після пошуку, зміни фільтра, пагінації, серверного оновлення і повернення.
- Narrator читає значення, eligibility, результат застосування й контекст кнопок.
- Pending/changed/selected/unavailable відрізняються не лише кольором.
- Читабельність disabled/read-only станів і фокус статистичного віджета.

**Preview і truthfulness**
- Скіни різних моделей рук, усі броні, зброя, shield, resize та modal return.
- Відповідність preview і фактичної серверної видачі.
- Перевірка показаних параметрів здібностей на чинній реалізації, без неявного балансування.
- Стартові stats чітко відділені від умовних бойових ефектів.
